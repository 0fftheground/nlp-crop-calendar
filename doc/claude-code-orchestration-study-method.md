# Claude Code Orchestration 学习方式约定

## 目的

这份文档不是在总结 Claude Code 的代码本身，而是在固化当前这套**学习和记笔记的方法**，方便以后在别的电脑上继续学习时，保持同一套分析口径、文档结构和表达标准。

目标是避免以下问题：

- 换电脑后忘了现在是怎么学的
- 总览和分阶段笔记写法混在一起
- 笔记里出现过多抽象词，缺少对应实现动作
- 每次继续学习时，又重新摸索一遍笔记格式

---

## 当前学习对象

当前学习主题是：

```text
Claude Code 的 orchestration layer
```

当前学习方式不是“泛泛看架构”，而是：

```text
先建立抽象的阶段结构
再按阶段逐个梳理
并用具体代码实现辅助理解每个阶段的数据和状态传递
```

## 学习顺序

当前采用的是**按 orchestration 主干阶段顺序学习**，而不是按源码文件顺序学习。

主干顺序是：

```text
原始输入
→ Turn 接收
→ 输入预处理
→ 会话写入
→ 执行前持久化
→ 静态上下文构建
→ Runtime 交接
→ Runtime 主循环
→ 消息回流
→ 事件输出适配
→ 状态更新
→ 结果输出
```

也就是说，继续学习时优先问：

```text
当前正在主干链路的哪个阶段？
```

而不是先问：

```text
这个函数在哪个文件里？
```

---

## 总览笔记的写法

`Orchestration Layer 总览` 这类笔记，必须保持**抽象架构视角**。

总览里应该写：

- 这一层的定位
- 主干执行链路
- 核心对象
- 横向控制轴
- 阶段之间的大结构关系

总览里**不要**把具体函数名当成主描述方式，例如：

- `QueryEngine.submitMessage(...)`
- `processUserInput(...)`
- `recordTranscript(...)`

这些实现细节可以在分阶段笔记里出现，但不应该成为总览的主框架。

一句话原则：

```text
总览负责讲结构，不负责讲代码细节。
```

---

## 分阶段笔记的写法

每个阶段单独记一篇。

分阶段笔记必须允许使用**具体代码实现**来辅助理解这一阶段：

- 调用了什么函数
- 改了什么字段
- 返回了什么对象
- 下一阶段拿到的是什么数据

也就是说，分阶段笔记不是纯抽象描述，而是：

```text
用实现细节解释这个阶段到底做了什么
```

一句话原则：

```text
分阶段笔记负责讲“这一层具体怎么做”。
```

---

## 分阶段笔记的固定结构

以后每篇阶段笔记，尽量保持下面这个结构：

```text
1. 本层涉及的关键代码对象
2. 目标
3. 结果
4. 过程
5. 与相邻阶段的衔接
6. 可复用建议
7. 一句话总结
```

含义分别是：

### 1. 本层涉及的关键代码对象

回答：

```text
这一层里马上会出现哪些代码对象、字段、函数或中间变量？
```

这个小节的目的不是展开实现细节，而是先做一个最小导览，避免正文一上来就出现：

- `QueryEngine`
- `processUserInput(...)`
- `this.mutableMessages`
- `recordTranscript(...)`

这类对象时显得突兀。

写法要求：

- 放在每篇分阶段笔记最前面
- 只做简短铺垫
- 说明它在这一层里为什么重要

### 2. 目标

回答：

```text
这一层要解决什么问题？
```

### 3. 结果

回答：

```text
这一层完成后，系统进入了什么状态？
```

### 4. 过程

回答：

```text
这一层具体做了哪些实现动作？
```

这里可以落到：

- 函数调用
- 字段更新
- 中间变量
- 返回值结构

### 5. 与相邻阶段的衔接

回答：

```text
这一层承接上一层的什么？
这一层向下一层交出什么？
它和相邻层的边界是什么？
```

这是当前学习里后来补强的重点，不能省略。

### 6. 可复用建议

回答：

```text
如果以后自己做 AI agent / AI application，
这一层的哪些设计值得借鉴？
```

### 7. 一句话总结

要求一句话压缩这一层的本质。

## 表达风格约定

### 1. 总览抽象，分阶段具体

这是最重要的一条。

- 总览：抽象架构视角
- 分阶段：具体实现视角

不能反过来。

### 2. 少用模糊词，多写具体动作

在分阶段笔记里，尽量少写这些词：

- 纳入
- 绑定
- 挂到
- 放进作用域
- 成为基础
- 提供归属

除非后面立刻解释：

```text
到底是哪个字段被改了？
哪个函数被调用了？
哪个数组被 push 了？
哪个对象被构造出来了？
```

更好的写法是直接写：

- 调用了什么函数
- 读取了哪些字段
- 返回了什么数据
- 修改了哪个数组或对象

### 3. 能写“数据怎么流动”就不要只写“语义上发生了什么”

比如不要只写：

```text
这一层把输入纳入当前会话
```

要尽量写成：

```text
这一层把 processUserInput(...) 返回的 messages
push 到 this.mutableMessages
```

### 4. 抽象说明和实现说明要分开

一种比较稳的写法是：

- 先说这一层的抽象职责
- 再说 Claude Code 里对应的具体实现动作

这样既不会丢结构，也不会太空。

## 输出习惯约定

以后继续学习时，默认遵守下面这条：

```text
不要先把完整内容直接输出到对话框，
优先直接写到 md 文件。
```

也就是说：

- 学完一个阶段
- 或补充一段笔记
- 或修正一篇已有笔记

优先直接落文件，再在对话里说明更新了什么。

## 当前已经确认的边界标准

### 1. `Orchestration Layer 总览`

- 保持抽象
- 不以具体函数名作为主框架

### 2. `Turn 接收`

- 要明确输入不只是 `string`
- 需要写清：
  - `submitMessage(...)` 接收什么
  - 它读取了哪些当前引擎字段
  - 它把什么参数交给输入预处理

### 3. `会话写入`

- 不要只写“并入 session”
- 要写清：
  - 哪个数组被改了
  - 后续代码读的是哪份 messages

### 4. `执行前持久化`

- 不要只写“留下 durable anchor”
- 要写清：
  - 写的是 transcript
  - 调的是 `recordTranscript(...)`
  - 某些情况下还会 `flushSessionStorage()`

## 继续学习时的推荐工作流

以后在别的电脑上继续时，建议按这个顺序继续：

1. 先打开这份文档，确认当前学习方式
2. 打开 `Orchestration Layer 总览`
3. 确认当前已经学到哪个阶段
4. 按主干顺序继续下一阶段
5. 先写该阶段的抽象职责
6. 再补具体实现动作
7. 最后补“与相邻阶段的衔接”

如果发现某篇旧笔记里有这些问题：

- 用词过于抽象
- 没写清字段变化
- 没写清函数调用
- 没写清和上下游的关系

优先回改旧笔记，不要带着模糊点往后走。

---

## 一句话总结

> **现在这套学习方式的核心，不是按文件看代码，而是按 orchestration 的主干阶段学习：总览保持抽象，分阶段笔记落到具体实现，并且每一层都写清和前后阶段的数据与状态衔接。**
