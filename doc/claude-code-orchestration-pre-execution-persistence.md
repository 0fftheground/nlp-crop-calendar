# 执行前持久化

## 目标

执行前持久化这一层要解决的问题是：

> **在真正进入 runtime 主循环之前，为这次 turn 留下可恢复、可追踪、可回放的持久化基础。**

它关心的不是：

- 模型怎么推理
- 工具怎么执行
- 最终回答是什么

它关心的是：

```text
如果后面执行过程中断、失败、崩溃、被 compact、需要 resume，
系统有没有一个足够早的落点，
能证明“这一轮已经开始了”。
```

所以这一层本质上是在做：

```text
本轮执行真正开始前
→ 先留下 durability / recovery / transcript 基础
```

---

## 结果

这一层完成之后，系统至少会进入下面这种状态：

- 当前 turn 已经拥有一个可追踪的持久化入口
- 这轮执行不是只存在于内存里，而是已经有了某种可恢复依据
- 后续就算 query loop 中途失败，也不至于完全丢失“这轮已经开始”的事实
- transcript / session storage / resume 机制可以围绕这一轮继续工作

所以它的结果不是“保存最终结果”，而是：

> **为这轮执行建立一个足够早的持久化锚点。**

---

## 过程

结合 Claude Code 的整体结构来看，执行前持久化更适合被理解为：

```text
在进入 query / queryLoop 之前，
把这轮 turn 的关键会话事实先落到可恢复体系里
```

这一层大致包含下面几类动作。

### 1. 持久化的对象不是“最终答案”，而是“执行起点”

执行前持久化最重要的一点是：

它保存的不是：

```text
assistant 的最终输出
```

而是：

```text
这一轮输入已经进入系统并准备执行
```

所以这里更像是在记录：

- 当前 session 继续向前推进了一轮
- 当前 turn 已经正式开始
- 当前 message state 已经发生变化

它解决的是“起点丢失”问题，而不是“结果存档”问题。

### 2. 为 session storage / transcript 留下早期锚点

Claude Code 的执行过程不是无状态的临时调用，而是带：

- session
- transcript
- compact
- recovery
- resume
- tool result 回流

的一整套持续执行体系。

因此在进入 query loop 之前，系统需要先让后续这些机制知道：

```text
本轮已经存在
```

这一步的意义可以理解成：

```text
给 transcript / session storage / recovery 系统一个最早可见的锚点
```

这样后面无论是：

- 继续执行
- 崩溃中断
- 用户恢复
- compact 后继续

系统都不是从“完全没有这轮记录”的状态开始补救。

### 3. 它和会话写入的区别

这一点特别容易混。

### 会话写入更偏：

```text
把 turn-ready 输入并入当前 session 的运行态 message 集合
```

### 执行前持久化更偏：

```text
把“这一轮已经开始”的事实写入 durability / replay / recovery 体系
```

也就是说：

- 会话写入首先面向 **当前运行态**
- 执行前持久化首先面向 **未来恢复与回放**

所以这两层虽然相邻，但视角不同。

### 4. 它通常发生在 Runtime 主循环之前

如果按主干顺序理解：

```text
Turn 接收
→ 输入预处理
→ 会话写入
→ 执行前持久化
→ 静态上下文构建
→ Runtime 交接
```

那么执行前持久化的关键位置就在：

```text
真正进入 query / queryLoop 之前
```

这很重要，因为如果进入 runtime loop 之后才第一次持久化，那一旦前面发生崩溃：

- 本轮开始信息可能丢
- transcript 可能断档
- recovery 入口会变弱

所以执行前持久化的目标，就是把这个风险前移处理掉。

### 5. 它不一定意味着“重型落盘”

执行前持久化不一定等于：

- 写数据库大对象
- 存完整上下文快照
- 保存所有工具状态

更常见的理解应该是：

```text
先留下一个最小但足够有用的 durable record
```

这个记录至少应该能帮助系统回答：

```text
这轮 turn 是否已经开始？
它属于哪个 session？
这一轮最初写入了哪些核心 message？
```

所以这一层更强调：

```text
早
```

而不一定强调：

```text
全
```

### 6. 为后续状态演化提供“可回放起点”

Claude Code 后续会发生很多状态变化，例如：

- assistant message 生成
- tool use
- tool result
- compact
- interruption
- resume
- usage 更新

这些都属于“执行中的状态演化”。

而执行前持久化做的是：

```text
先把状态演化的起点固定下来
```

这样后续即使状态不断变化，系统仍然知道：

```text
这一轮最开始是从哪里进入运行态的
```

所以它更像：

> **一次 turn 的 durable 起点登记。**

---

## 可复用建议

如果以后自己做 AI agent / AI application，这一层有几条非常值得直接借鉴。

### 1. 把“进入执行”之前的 durable anchor 单独建层

不要等最终结果出来才做持久化。

更稳的做法是：

```text
一轮 turn 准备正式执行前
先记录一个 durable start point
```

这样后续做：

- resume
- replay
- debugging
- audit

都会轻松很多。

### 2. 先追求“足够恢复”，不要一开始追求“全量快照”

执行前持久化最重要的是：

```text
能证明这轮已经开始，并能找到恢复入口
```

而不是一开始就试图把 runtime 全部状态完整序列化。

也就是说，这一层更适合先做：

```text
最小可恢复记录
```

### 3. 把运行态写入和 durability 写入区分开

这是特别值得学的边界：

- 会话写入：面向内存中的当前 session state
- 执行前持久化：面向未来恢复和回放

如果把这两层混成一个动作，后面通常会出现：

- 状态边界不清
- 恢复逻辑混乱
- transcript / runtime 职责缠绕

### 4. 把它视为 replay 系统的一部分，而不只是 storage 细节

执行前持久化真正有价值的地方，不是“存了什么”，而是：

```text
它让这轮执行具备被重建、被解释、被回放的可能
```

这对 agent 系统尤其重要，因为 agent 不只是给答案，还会：

- 连续执行
- 调工具
- 修改状态
- 中断恢复

所以这一层最好从一开始就用“replay / recovery 视角”理解，而不是“数据库写入视角”。

### 5. 位置要前，但职责要轻

它应该发生得足够早，但不要让它变成一个重型的总控层。

更好的做法是：

```text
在 runtime loop 前快速留下 durable start point
然后尽快把控制权交给后续链路
```

这样既能保证恢复能力，又不会拖慢主控结构。

---

## 一句话总结

> **执行前持久化的本质，不是保存最终执行结果，而是在本轮真正进入 runtime 主循环之前，先为这次 turn 建立一个可恢复、可追踪、可回放的 durable 起点。**
